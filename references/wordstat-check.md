# Проверка частотности Wordstat — scripts/wordstat_check.py

Официальный платный метод Яндекса (Yandex Cloud Search API v2), не парсинг и не серая
зона. Источник реализации и договорённостей по API — сервис [KeyWai](https://github.com/AndreyTsibin/keywai)
(`backend/apps/parsing/services/wordstat.py`), сюда вынесен только нужный минимум: без
Docker/Django/Postgres, чистый Python-скрипт.

## Получение ключа

1. Консоль <https://console.cloud.yandex.ru/> → создать **каталог** (folder).
2. Создать **сервисный аккаунт**, выдать роль **`search-api.webSearch.user`**.
3. Создать для аккаунта **API-ключ**.
4. `cp scripts/.env.example scripts/.env`, заполнить `YANDEX_SEARCH_FOLDER_ID` и
   `YANDEX_SEARCH_API_KEY`.

VPN не нужен — сервис доступен из РФ напрямую.

## Стоимость

- `topRequests` (частотность + связанные фразы) — ~20 ₽ за 1000 запросов.
- `getRegionsTree` (список регионов) — бесплатно.
- Скрипт не кеширует — каждый повторный запрос той же фразы снова платный. Для
  разовых/точечных проверок в рамках аудита это не критично; при регулярном сборе
  большого ядра — кешируй результаты руками (например, сохраняй JSON-вывод в файл).

## Использование

```bash
# частотность фразы, вся Россия, все устройства
python scripts/wordstat_check.py "купить телефон"

# конкретные регионы (213 = Москва, 1 = Москва и область — см. --regions-tree) и устройства
python scripts/wordstat_check.py "купить телефон" --regions 213,1 --devices desktop,mobile

# список регионов, чтобы найти нужный ID (бесплатно)
python scripts/wordstat_check.py --regions-tree

# машиночитаемый JSON — для передачи дальше в обработку
python scripts/wordstat_check.py "купить телефон" --json

# пакетная проверка списка фраз за один прогон (не писать одноразовый скрипт на каждый разбор)
python scripts/wordstat_check.py --batch-file phrases.txt --regions 38 --out results.json
```

Требуется пакет `requests` (`pip install requests`, если ещё не стоит).

## Пакетный режим (`--batch-file`)

Собирая ядро на десятки фраз, не пиши каждый раз новый python-скрипт с ручным циклом и
`time.sleep` — это уже встроено. `phrases.txt` — по одной фразе на строку, `--delay`
(по умолчанию 1 сек) держит частоту в пределах официального лимита (см. «Rate limit» ниже),
`--out` сохраняет результат в JSON для дальнейшей обработки. Прогресс печатается построчно
по мере готовности (`flush=True`) — если запускаешь батч в фоне, сразу видно, что процесс
не завис, а не только после завершения всего списка.

## Ограничения

- Нет `negative_prompt`-аналога — метод просто отдаёт данные, фильтрация фраз (мусор,
  нерелевантные интенты) — на стороне того, кто анализирует вывод.
- `numPhrases` — максимум 2000 за один вызов.
- Ошибки 401/403 и прочие 4xx — скрипт останавливается сразу с понятным сообщением, здесь
  повторять нечего (неверный ключ/роль не исправится повтором).

## Rate limit (429) — обрабатывается автоматически

Официальный лимит API — **10 запросов/сек, 10 000/час** на синхронные запросы, включая
`topRequests` (aistudio.yandex.ru/docs/ru/search-api/concepts/limits). Это не квота на
ключ/аккаунт в смысле «столько-то в принципе» — это скорость: 429 почти всегда означает
всплеск запросов чаще лимита, а не исчерпанный дневной/часовой бюджет (на разбор одного
ядра из полусотни фраз до часового потолка далеко).

`call_api()` в `wordstat_check.py` сам делает retry с экспоненциальным бэкоффом (до 5 попыток,
уважает `Retry-After`, если он есть в ответе) — писать свой backoff вокруг вызова скрипта не
нужно. При батч-проверке (`--batch-file`) держи `--delay` не меньше умолчания (1 сек) —
это уже с запасом ниже 10/сек, повторных 429 почти не будет.

Квоту саму по себе можно поднять только через обращение в поддержку Яндекс.Облака —
самостоятельного тумблера в консоли нет. Для объёмов в рамках SEO-аудита (десятки–сотни
фраз за сессию) в этом нет смысла — дефолтного лимита хватает с большим запасом, проблема
почти всегда в собственной частоте запросов, не в потолке квоты.

⚠️ **Замечено на практике 05.09.2026**: после серии батчей без пауз (несколько скриптов
подряд, часть с задержкой 0.3 сек между вызовами) счёт на этом ключе словил 429 даже на
одиночный свежий запрос, сделанный через много минут после последнего успешного вызова, и
не отпустило после полного цикла бэкоффа (5 попыток, суммарно ~93 сек ожидания). Это не
укладывается в модель «10 запросов/сек — подождал секунду, поехали дальше»: похоже, что
после заметного всплеска включается более длинное штрафное окно (минуты, не секунды), либо
у этого конкретного ключа фактический лимит ниже документированного по умолчанию. Если
видишь 429 на первом же запросе после долгой паузы — не гоняй `--batch-file` дальше сразу,
выдержи паузу в несколько минут (5–10) и попробуй один одиночный запрос перед тем, как
возвращаться к батчу.
