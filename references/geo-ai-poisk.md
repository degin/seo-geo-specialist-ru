## Три кластера GEO для РФ

**Структура** — Ответ в начале (первые 1000 символов — прямой ответ на главный запрос), формат для парсинга (H2/H3, списки, таблицы, блоки «Вопрос-Ответ», структура «Ответ → Детали → Вывод»), Schema-разметка (см. [json-ld-шаблоны](../references/json-ld-shablony.md)).

**Доверие** — E-E-A-T сигналы, «приманки для цитирования» (оригинальная статистика, экспертные цитаты, чёткие определения, сравнения «А vs Б»), свежесть (обновление минимум раз в квартал).

**Локальность** — гео-контекст (город, адрес, телефон, геометки) для попадания в локальные ответы Алисы; формулировки под голосовой поиск («как выбрать...», «сколько стоит...»); видео с текстовой расшифровкой.

## AI-краулеры и robots.txt

Это прямой рычаг: если бот-краулер конкретной ИИ-системы заблокирован в robots.txt, бренд физически не может попасть в её ответы и цитирования — независимо от качества контента. Но обратное тоже верно не всегда: разрешить бота — не значит автоматически получить трафик, это необходимое, но не достаточное условие.

**Логика принятия решения по каждому боту:** оцени, даёт ли этот ИИ-сервис реальный обратный трафик/цитирование источника, или только забирает контент на обучение без отдачи. Для большинства коммерческих сайтов в РФ разумный дефолт — разрешать краулеры, которые цитируют с указанием источника (это работает как бесплатный охват), и настороженно относиться к тем, что только обучаются без обратной ссылки.

⚠️ **Имена User-Agent меняются быстрее, чем обновляется этот файл.** Таблица ниже — состояние на момент составления (август 2026) по публично документированным ботам крупных ИИ-компаний; часть строк (особенно у Anthropic — там несколько похожих имён) отмечена как требующая проверки. Перед тем как вставлять правила в реальный robots.txt клиента: 1) сверь актуальное написание имени в свежей документации компании, 2) посмотри логи сервера клиента — какие боты реально заходят и под каким именем представляются (это надёжнее, чем любая таблица, включая эту).

| `CCBot` | Common Crawl | Датасет, на котором тренируется множество моделей (в т.ч. открытых) | **Нейтрально, решение по ситуации** | Не даёт прямого цитирования назад, но массово питает обучающие корпуса — обсуди с клиентом, насколько это принципиально |

Важно: правила ИИ-краулеров добавляются **дополнительными блоками**, не трогай существующие директивы для Googlebot/YandexBot — эти боты должны оставаться Allow (или с уже принятыми клиентом ограничениями) независимо от решений по ИИ.

**Tilda (tilda.cc) — редактировать robots.txt технически нельзя вообще, ни для одного бота.** Официальный ответ поддержки Tilda: «Есть ли возможность отредактировать файл robots.txt? К сожалению, в данный момент такой возможности в Тильде нет. Единственный вариант внести кардинальные изменения — экспортировать проект на собственный хостинг» ([tilda.cc/ru/answers/a/robots-edit](https://tilda.cc/ru/answers/a/robots-edit/)). Вся таблица и шаблон выше на Tilda-проектах не применимы как набор правок — по факту там implicit-allow для всех ботов, которых Tilda не блокирует своими служебными правилами, и точечно управлять этим нельзя. Единственный смежный рычаг — чекбокс «Запретить поисковикам индексировать эту страницу» в настройках конкретной страницы (Facebook & SEO) — это page-level noindex одной страницы, а не per-bot Allow/Disallow, под задачу разрешить/запретить конкретных ИИ-краулеров он не годится. На аудите/ТЗ для Tilda-клиента сразу говори это ограничение платформы, не предлагай несуществующую настройку. Второй Tilda-специфичный факт из этого раздела GEO — про `llms.txt` — см. ниже.

## llms.txt

Отдельный файл (не путать с robots.txt) — краткая выжимка о сайте/бренде на понятном модели языке, которую отдают по `/llms.txt` (и опционально более подробную версию по `/llms-full.txt`). Ослабляет проблему «модель ничего не знает о бренде», о которой предупреждает `robots.txt`-таблица выше по `GPTBot`, но не заменяет остальной GEO из этого файла — это дополнительный явный сигнал, а не альтернатива структуре страниц/цитируемости/Schema.

**Tilda (tilda.cc) — нативная поддержка, ничего вручную выкладывать не нужно.** Настройки сайта → «Управление файлами llms.txt и llms-full.txt»: два текстовых поля — LLMS.TXT и LLMS-FULL.TXT. Заполнил → «Сохранить» — Tilda сама отдаёт содержимое как plain text по `/llms.txt` и `/llms-full.txt`, без HTML-обёртки. Не нужны ни алиас-страница, ни блок с кодом, ни `tilda-helper` — это готовая панель в интерфейсе конструктора, а не кастомизация. Для клиентских сайтов на Tilda сразу веди сюда, не предлагай обходных путей через алиасы.

Для не-Tilda CMS — проверяй, есть ли у платформы аналогичная штатная функция, прежде чем предлагать самодельное решение (статический файл в корне, отдаваемый как plain text).

## Точная цитируемость текстовых блоков

Общее правило «первые 1000 символов — прямой ответ» касается только вступительного абзаца страницы. У остальных типов контента — свои оптимальные пороги длины, потому что ИИ-системы вырезают и цитируют разные единицы текста по-разному:

| Тип блока | Оптимальная длина | Зачем именно так |
|---|---|---|
| Вступительный прямой ответ (первый абзац) | 40–60 слов (≈300–450 символов) | Достаточно короткий, чтобы модель могла процитировать целиком как готовый ответ, не обрезая на середине мысли |
| Самодостаточный цитируемый абзац (в теле статьи, для AI Overviews / YandexGPT / Perplexity) | 130–170 слов (≈900–1200 символов) | Это объём, на котором абзац успевает раскрыть факт **и** контекст без отсылок вида «как сказано выше» — модель может вырезать его как отдельный чистый фрагмент |
| Ответ в блоке FAQ | 40–80 слов на один вопрос | Оптимально для голосового ответа Алисы и для того, чтобы ИИ-модель могла процитировать ответ целиком — длиннее не помещается в голосовой ответ. Не путать с «FAQ rich result» Google (сниппет-гармошка в выдаче) — эта фича с мая 2026 отключена у Google для всех сайтов, длина ответа тут ни при чём |
| Определение термина / глоссарий | 1–2 предложения, до 40 слов | Модели любят цитировать чёткие определения как есть — избыточный контекст в определении снижает шанс дословного цитирования |

Практическое правило при написании: каждый абзац, который потенциально может стать ответом ИИ-системы, должен **проходить тест на вырезание** — если вставить только этот абзац отдельно, без соседних, он должен оставаться понятным и фактически полным (субъект + утверждение + при необходимости источник — всё в одном фрагменте, без местоимений типа «это» и «такой подход», отсылающих к предыдущему абзацу).

## Триплеты для AI-выдачи

Каждая коммерческая страница должна содержать явные утверждения в формате:
- `[Бренд] → [Услуга] → [Условие]`
- `[Сущность] → [Атрибут] → [Значение]`

Где размещать: первый экран (заголовок + подзаголовок), блок «Преимущества» (список с явными атрибутами, не общими фразами), FAQ-блок (вопрос = атрибут, ответ = значение). ИИ-модели цитируют не «красивый текст», а чёткие факты с привязкой к сущности.

## Доверие: E-E-A-T сигналы

- Авторство с фото и регалиями (должность, опыт) — не анонимный «Редакция сайта»
- Кейсы с цифрами внедрения, а не общими формулировками «отличный результат»
- Ссылки на источники при любых цифрах/утверждениях
- Актуальные даты публикации и обновления
- «Приманки для цитирования»: оригинальная статистика, экспертные цитаты, чёткие определения, сравнения «А vs Б»

## Локальность и голосовой поиск

Гео-контекст (город, адрес, телефон, геометки) — обязателен для попадания в локальные ответы Алисы. Формулировки в стиле «как выбрать...», «сколько стоит...» — под голосовой поиск. Короткие видео-ответы с текстовой расшифровкой усиливают оба сигнала сразу.

## Бренд-авторитет для ИИ-поиска (RU)

Упоминания бренда коррелируют с видимостью в ИИ-ответах сильнее, чем классическая ссылочная масса — модель воспринимает часто упоминаемый бренд как признанный источник. Для РФ-инфополя мониторь и наращивай присутствие на следующих площадках (выбирай по аудитории клиента, не пытайся закрыть все сразу):

| Площадка | Когда приоритетна | Что делать |
|---|---|---|
| Habr | B2B, tech, IT-услуги | Экспертные статьи от лица специалиста компании (не рекламные), с кейсами и цифрами |
| VC.ru | B2B, стартапы, бизнес-аудитория | Кейсы, разборы рынка, колонки основателя. По практике 2026 года — самая «жирная» площадка для GEO из этого списка, приоритет по умолчанию для B2B/бизнес-ниш |
| DTF | Игры, IT-продукты, digital-аудитория помоложе VC.ru | Кейсы разработки, разборы продукта — площадка того же холдинга, что VC.ru, но другой демографический профиль |
| Клерк.ру | Бухучёт, юридические, финансовые услуги | Экспертные статьи по профилю ниши — площадку одинаково любят и Яндекс, и Google, и нейросети, приоритетна именно для этой вертикали |
| TenChat | B2B-нетворкинг, услуги для бизнеса | Профиль эксперта/компании + регулярные посты, площадка изначально заточена под деловые контакты |
| Дзен | B2C, широкая аудитория | Регулярные публикации, вопрос-ответ формат |
| Pikabu | B2C, вирусный охват | Только если у бренда есть история/юмор, органично заходящая в формат площадки |
| Тинькофф Журнал | Финансы, потребительские товары/услуги | Высокий редакционный барьер входа (не берут любой текст), но сильный сигнал доверия при публикации |
| Яндекс Q | Любая ниша с частыми вопросами аудитории | Развёрнутые ответы от лица эксперта компании на профильные вопросы |
| 2ГИС, Яндекс.Карты | Локальный/офлайн бизнес | Стимулировать отзывы, обязательно отвечать на каждый — ответ на отзыв тоже сигнал доверия для ИИ и для клиента |
| Otzovik, IRecommend, Фламп | Товары и услуги массового спроса | Мониторинг + работа с негативом, не игнорировать |
| Wikipedia (ru) | Только крупный/узнаваемый бренд | Попасть сложно, но сигнал очень сильный — реалистично для клиентов с историей и внешними независимыми упоминаниями в СМИ |
| Telegram-каналы отрасли | Любая ниша с активным тематическим комьюнити | Упоминания и гостевые посты у профильных каналов |

Действия по мониторингу:
- Раз в месяц — ручные тесты 15–20 брендовых и продуктовых промптов в Алисе, YandexGPT, ChatGPT, Perplexity, Gemini: цитируют ли бренд, в каком контексте, с ошибками или без
- Настроить оповещения на упоминания бренда (там, где доступно в РФ-контуре)
- Отслеживать брендовый спрос в Яндекс.Вордстате как индикатор растущей узнаваемости
- **Диагностика точечного отсутствия** — если конкретный запрос упорно не показывает бренд там, где логично ожидать (профильный рейтинг, сравнение с конкурентами), спроси саму модель напрямую, почему бренд не попал в её ответ. Не всегда даёт точный ответ, но иногда указывает на конкретный пробел (нет свежих упоминаний, нет структурированных данных на сайте) быстрее, чем догадки по чек-листу.

**Что не предлагать под видом продвижения на этих площадках** — юридический и репутационный риск, не рабочая техника:
- **Собственные сайты-рейтинги** («топ-5 лучших [ниша] в [город]») на отдельных доменах под конкретного клиента — по сути замаскированная самореклама, подпадает под запрет недобросовестной конкуренции (гл. 2.1 135-ФЗ «О защите конкуренции» — дискредитация конкурентов и введение потребителя в заблуждение). Если у ниши уже есть независимые рейтинги — работай на попадание в них (раздел выше), не создавай свои.
- **Покупные места в чужих рейтингах** и **тиражирование заказных публикаций** о персональном бренде эксперта без пометки «реклама» — с 01.09.2022 действует обязательная маркировка интернет-рекламы через ЕРИР (поправки в 38-ФЗ «О рекламе»), она касается и native-форматов, не только явных баннеров. Если материал оплачен для продвижения — маркировка обязательна, это не решение на усмотрение клиента.

## AI-агенты Google — новый риск

Google I/O 2026 запустил «information agents» — ИИ-агенты, которые мониторят интернет 24/7 вместо пользователя. Пользователь получает подписку на события («следи за тендерами в моей нише», «мониторь отзывы о конкурентах»), а не повторяющиеся поисковые запросы. Риск: пользователь перестаёт возвращаться на сайт — Google становится подпиской, а не воротами трафика.

Действие: строить бренд как источник, а не как страницу; давать уникальные данные, которые нельзя собрать автоматически; работать на цитируемость в AI-ответах.

## Агентная готовность (Agentic Browsing)

Отдельный от остального GEO/AEO трек. Всё выше в этом файле — про то, чтобы ИИ **процитировал или порекомендовал** бренд в ответе. Здесь — про то, что ИИ-**агент** (браузерный агент вроде Claude/Operator-класса, или агент на платформе пользователя) должен суметь **довести действие до конца на самом сайте**: оформить заявку, забронировать столик, положить товар в корзину и оплатить — без участия человека. Это разные задачи: страница может отлично цитироваться в Алисе и при этом быть непроходимой для агента, который пытается на ней что-то сделать.

**Зачем это в SEO-аудите, а не только в разработке.** Диагностика готовности — это чтение сайта глазами агента (структура, тексты, разметка), то есть SEO-компетенция. Внедрение исправлений интерфейса (Tilda) — уже `tilda-helper`; интеграция с CRM/1С для живых цен и остатков, права доступа агента, защита от промпт-инъекций в контенте — это разработка/безопасность, не входит в этот скилл. Проговори с клиентом, где проходит граница.

**Что проверять:**

- **Источник критичных данных.** Цена, наличие, расписание, статусы заказа — если это статичный текст, который правится руками раз в квартал, агент либо получит устаревшие данные, либо не сможет проверить актуальность и откажется от действия. Спроси: откуда на сайте берётся цена/остаток — из CRM/1С/API или вписана в вёрстку.
- **Единство данных между источниками.** Цена/режим работы/контакты должны совпадать на сайте, в Яндекс.Бизнесе, 2ГИС. Агент может свериться с несколькими источниками и на расхождении просто остановиться — не как ошибка агента, а как сигнал недоверия к данным.
- **Устойчивый интерфейс** — агент читает DOM и accessibility-дерево, не картинку:
  - у кнопок действия есть текстовая подпись («Забронировать», «Оставить заявку»), не только иконка без `aria-label`/`alt`;
  - элемент не спрятан за динамической подгрузкой без предсказуемого момента готовности (для Tilda — блоки, ждущие `t_onFuncLoad`/лениво подгружаемые при скролле, могут быть «невидимы» агенту в момент клика, если он не дождался события);
  - после действия — явный **текстовый** статус результата («Заявка №1234 отправлена», «Ошибка: заполните телефон»), а не только визуальная анимация/цветовая индикация, которую агент не считает по DOM.
- **Транзакционная Schema-разметка** — Product/Offer с актуальными `price`/`availability`, Service где применимо (шаблоны — [json-ld-shablony.md](../references/json-ld-shablony.md)). Разметка без реальных данных за ней (см. пункт про источник данных) агенту не поможет — он либо это заметит, либо совершит действие на неверных условиях, что хуже.

**Инструмент диагностики:** Chrome DevTools → Lighthouse → категория Agentic Browsing (проверь актуальное название категории на момент аудита — интерфейс Lighthouse меняется быстрее референса). Дополняет, не заменяет ручную проверку DOM-структуры и текстовых подписей выше.

**Приоритизация под клиента.** Высокий приоритет — если у клиента уже есть повторяющаяся цифровая операция (запись, заказ, бронь) с данными в рабочей системе, и конкуренты заметно двигаются в эту сторону. Низкий приоритет — если данные ведутся вручную и на сайте вообще нет цифровой операции (только визитка/лендинг под звонок) — тогда сначала обычная техническая гигиена сайта, агентная готовность подождёт.

### Чек-лист: сайт готов к транзакционным ИИ-агентам

- [ ] Цена/наличие/расписание берутся из рабочей системы (CRM/1С/API), не устаревают в статичной вёрстке
- [ ] Данные (цена, контакты, режим работы) совпадают на сайте и во внешних карточках (Яндекс.Бизнес, 2ГИС)
- [ ] Кнопки действия имеют текстовую подпись или `aria-label`, не только иконку
- [ ] Блок с формой/ценой не скрыт за динамической подгрузкой без предсказуемого момента готовности
- [ ] После отправки формы/брони — явный текстовый статус успеха или ошибки, читаемый из DOM
- [ ] Транзакционные сущности размечены Schema.org (Product/Offer с `price`/`availability`, Service)
- [ ] Пройдена проверка Chrome Lighthouse → Agentic Browsing (если категория доступна в текущей версии инструмента)

## Инструменты в SERP — зона риска

Google строит калькуляторы, сравнения, маршруты прямо в выдаче — это убивает трафик информационных инструментов (калькуляторы ипотеки/калорий, подборки «как выбрать», «топ-10», сравнения товаров).

Действие: информационные страницы перестраивать так, чтобы они вели к действию (не «что такое CRM», а «CRM для отдела продаж до 10 человек — цена, внедрение, заявка»). Коммерческие страницы закрывать намерение полностью: цена, сроки, кейсы, отзывы, гарантии, сравнение, форма заявки.

## Уникальная ценность как SEO-актив

ИИ пересказывает интернет, но не может заменить реальный опыт — это новый SEO-актив. Что любит ИИ-поиск: собственные тесты и скриншоты, реальные цены из практики, кейсы с цифрами внедрения, честные «кому НЕ подойдёт», выводы специалиста, а не рерайт конкурентов. Принцип: нейросеть перескажет чужой текст, реальный опыт — нет.

## Экспресс-проверка: страница в зоне риска?

Возьми топ-страницу и спроси: пользователь пришёл за информацией или за действием?
- За информацией («что такое», «как выбрать») → **высокий риск**, ИИ заберёт ответ в выдачу
- За действием («купить», «цена под ключ», «запись») → **низкий риск**, поиск всё равно ведёт на сайт

Действие: информационные страницы перестраивать в коммерческие или гибридные.

## Мониторинг цитируемости

Инструменты ручных тестов промптов + при доступности — Brand24, Profound, Ottimo (западные сервисы, проверяй доступность/оплату из РФ на момент использования, не считай доступными по умолчанию). Провести аудит топ-10 страниц на соответствие принципам GEO — приоритет коммерческим страницам с высоким трафиком.

## Чек-лист готовности к ИИ-поиску

- [ ] Структура: списки, таблицы, заголовки
- [ ] Schema-разметка на ключевых страницах ([шаблоны](../references/json-ld-shablony.md))
- [ ] Авторство и экспертиза указаны явно
- [ ] Контент обновлён в последние 3 месяца
- [ ] Есть блок «Вопрос-Ответ» с частыми запросами
- [ ] robots.txt осознанно настроен под нужных ИИ-краулеров (см. таблицу выше)
- [ ] Цитируемые абзацы проходят «тест на вырезание» (см. раздел про точную цитируемость)
