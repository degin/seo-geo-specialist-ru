# Яндекс.Метрика / Вебмастер — прямой доступ через API

Когда у проекта есть API-токен на просмотр (не только доступ в интерфейс) — дёргать
API напрямую вместо ручного чтения отчётов: быстрее, точнее (без округлений виджетов
интерфейса), пригодно для сверки нескольких метрик и сегментов разом. Токен и общая
инструкция по доступам студии — в личном CLAUDE.md пользователя, здесь не хранится.

## Эндпоинты

- Метрика Stat API: `https://api-metrika.yandex.net/stat/v1/data`
- Счётчики (узнать `id` под конкретный домен): `https://api-metrika.yandex.net/management/v1/counters`
- Вебмастер API v4: `https://api.webmaster.yandex.net/v4/user/<user_id>/...` (hosts, indexing, search-queries)

Не у каждого сайта студии есть счётчик именно на домен сайта (иногда есть только
Метрика на карточку Яндекс.Карт) — проверять по полю `site` в ответе `/counters`,
не полагаться на название счётчика.

## Известные грабли (проверено практикой, не из документации)

**«Query is too complicated» на многодневных/многометричных запросах.** Stat API
отказывает на широких запросах (30 дней, несколько метрик разом) без явной
группировки. Решение — добавить `group=week` (или любую другую явную группу):
ошибка уходит, данные агрегируются корректно.

**Метрика цели — ID встроен в имя метрики, не отдельный параметр.** Интуитивно
ожидаемое `metrics=ym:s:goalReaches&goal_id=123` возвращает ошибку 4002
«Incorrectly specified metric». Правильно: `ym:s:goal123reaches`,
`ym:s:goal123conversionRate` — id цели прямо в имени метрики.

**Фильтр по dimension через `==` может тихо давать 0 при формально верном
синтаксисе.** Замечено на `ym:s:regionCountry=='Russia'` — валидный запрос, 0 визитов,
хотя трафик из России реально есть (вероятная причина — внутреннее значение enum не
совпадает с отображаемым названием, не подтверждено документацией). Обходной путь —
не фильтровать на сервере, а группировать по dimension (`dimensions=ym:s:regionCountry`)
и агрегировать нужный срез в коде на своей стороне.

## Методология: проверка целей/воронки — не верить первому нулю

Перед тем как констатировать «воронка сломана» (0 срабатываний по ключевым целям в
Метрике), проверь весь список целей в интерфейсе (Цели → полный список), не только
те, что были названы в брифе клиента или показались первыми. У проекта почти всегда
есть несколько параллельных механизмов постановки целей на одно и то же действие —
старые вручную настроенные (часто заброшенные при смене верстальщика/CMS) и
ecommerce/автоцели (`ym:s:goal<ID>reaches` с другими ID, `dataLayer`-события,
автособираемые по действиям на странице). 0 по одному набору ID — не факт поломки
всей аналитики, а сигнал проверить остальные наборы прежде чем формулировать находку.

Практика (1sm.ru, 11.09.2026): первая проверка по 4 старым вручную настроенным целям
дала 0 срабатываний за 30 дней и выглядела как критичная поломка (🔴). Повторная
проверка по ecommerce- и автоцелям с другими ID нашла реальную рабочую воронку
(десятки-сотни срабатываний). Находка была понижена до 🟡/🟢: «часть целей дублирует
друг друга, старые стоит удалить или перенастроить», а не «воронка не работает».
